# 第五阶段模拟支付与订单超时关单验收

验收日期2026-10-17，Windows、Java 21、Spring Boot 3、真实MySQL 8.4。基于既有main实现，保留Session Cookie、CSRF、单Maven及com.ticketing.order业务包，不接入真实支付平台，不产生实际扣款。

## 实现与核心文件

- OrderService：本人模拟支付、原成功流水重放、系统过期处理，复用原有锁序。用户操作检查ACTIVE，后台清理只加用户行锁。
- OrderMapper：数据库UTC时钟、带截止条件的PENDING状态更新、locked转sold及有界到期索引查询；PaymentMapper/PaymentRecord保存真实成功流水。
- OrderController：POST /orders/{id}/pay及GET /orders/{id}/payment，继承当前认证保护范围；拒绝客户端非空支付业务字段，金额只取订单快照。
- PaymentView、OrderView及TicketOrder映射：字符串金额/ID、UTC支付时间、simulated=true、canPay和JOIN读取的真实流水，不逐订单追加查询。
- OrderExpiryJob：Spring Scheduling、每单独立事务、失败隔离、按expires_at/id推进并回绕的扫描游标。
- Vue的OrderCard、OrdersView、api/orders.ts：模拟确认、最新状态校验、真实支付流水、截止后禁用、失败后重新查订单；现有活动/票档/个人中心及平台介绍的过时文案同步更新。
- OrderManagementIT新增12项支付/关单用例，原13项订单回归保留并将旧PAID/EXPIRED配额夹具改为真实支付及关单路径；OrderExpiryRecoveryIT验证应用关闭重启补偿。
- AGENTS、架构、数据库设计、API契约、计划、本地开发及.env.example已同步。数据库结构仍为V4，V1至V4未修改，没有创建无用V5或中间表。README及本地凭据继续忽略。

## 事务、截止与幂等

支付、主动取消、超时关闭均采用READ_COMMITTED，固定锁序为用户UPDATE→活动SHARE→场次SHARE→票档UPDATE→已有订单UPDATE。扫描仅发现候选，不先锁订单。管理员活动/场次/库存操作继续遵循父级优先协议。

支付在锁内检查本人和当前父级状态，最终SQL只在PENDING且expires_at大于UTC_TIMESTAMP(6)时转PAID。等待行锁跨过截止不能延长支付期限。随后条件更新locked减数量、sold加数量，插入唯一订单成功流水，金额来自订单totalAmountCents，paid_at与订单一致；任一步异常完整回滚。重复PAID直接返回原流水，不重复写入或变库存。后续SKU停售不撤销已占库存订单，但活动下架、场次取消或结束禁止继续支付待支付订单。

取消只从PENDING转CANCELLED，过期只在PENDING且expires_at小于等于数据库当前时间时转EXPIRED。两者只释放locked，不增加sold；与支付竞争最多一个终态生效，PAID仍占用户场次额度，CANCELLED/EXPIRED不再占额。核心库存不变量为locked/sold非负、locked+sold不超过total；可售量仍即时计算。

默认支付窗口15分钟，扫描启动立即执行，此后每批完成再等待30秒，默认100笔，上限500。使用idx_order_expiry(status,expires_at,id)，真实EXPLAIN验证索引被使用。每笔通过外部OrderService代理独立事务处理，失败回滚后记录并继续；游标即使失败也前进、扫到尾回绕重试，批量为1时坏单也不能阻塞后续订单。游标只是公平扫描位置，不保存业务事实，重启从数据库补偿。多个任务/实例可重复扫描，事务状态条件保证幂等。

系统清理不要求用户ACTIVE，禁用账号、活动下架或场次取消不阻止过期释放。没有RabbitMQ延迟消息、Outbox或Redis锁。截止到扫描成功之间可能仍PENDING并占库存，支付已被SQL拒绝，前端不能冒充已过期；积压、锁等待和持续数据错误可能延迟回收，需要检查任务日志。
