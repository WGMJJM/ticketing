# 第八阶段性能评估与优化分析

本次测量针对本机短时间闭环流量，不是生产容量承诺。复现见 [执行说明](01-reproduce.md)，完整阶段结果见 [系统验收](../15-performance-verification.md)，机器、软件、镜像摘要及MySQL配置见 [环境快照](results/hardware.json)。

## 环境与测量口径

Windows 11，i5-13400F，16逻辑处理器，31.82 GiB主机内存。Docker使用16逻辑CPU、约15.53 GiB内存。Java21.0.10、Maven3.9.9、k6 2.3.0、MySQL8.4.11；复用原有MySQL8.4、RabbitMQ4.1-management-alpine及Redis7-alpine镜像，没有更新镜像。JVM固定Xms512m/Xmx1024m及G1，Hikari前后均保持10，MySQL缓冲池128 MiB、最大连接151、flush-at-commit=1、sync-binlog=1。没有关闭持久化换取吞吐。

基线运行产物来自c0cd5d5，优化运行产物为该版本加本阶段最小发布器修改。每轮environment.json中的baseCommit表示工作区起点，实际运行jar以app.sha256区分；最终Git提交在阶段交付中记录。测试工具、窗口、数据规模和数据库服务配置保持一致。参数控制实验还使用同一个基线jar，分别只变更连接池或Outbox批量，避免将代码版本变化混入归因。

每档10秒预热、20秒稳定，10/25/50/100 VU。每轮重建1000条短文本活动及等价场次、库存、独立用户；混合场景轮转64场次，其他场景1场次。热点库存为100万张或5张。认证、Session Cookie、CSRF、幂等、支付、出票均走真实HTTP。关联操作跨独立数据库事务，最后检查MySQL事实。

稳定指标按**请求完成时间**截取窗口，RPS=稳定请求数/20，TPS=稳定期成功创建订单数/20。k6原始Counter.rate包含预热等时间，不用于稳定吞吐。P50/P95/P99来自稳定请求样本，未平均分位数。关联支付成功数可包含创建订单的收尾，只核对交易结果，不作为支付TPS。HTTP全部阶段的失败率也须为零，不能靠截断窗口隐藏超时。

预期409必须对应库存、限购、订单竞争或重复核销等已列明错误码。5xx、连接错误、未知冲突与鉴权错误均失败。核销负载是多管理员竞争**同一张票**，大量409是正确拒绝；其RPS不能当成不同票券成功入场容量。候补的HTTP RPS主要是轮询，实际分配和支付数量另行核对。

## 有证据的改动

定位到原Outbox每轮最多20条、轮后固定等待1秒，遇到持续取消产生的事件时，确认及数据库写入之外又受到批次停顿限制。50 VU混合基线在结束并继续观察30秒后仍有398条待投递。热点和混合场景的慢SQL集中在SKU锁等待与提交，并非Outbox缺少一个新索引。

50 VU混合场景的RabbitMQ就绪队列**采样峰值为0**，而Outbox待处理采样峰值为798，最终代码对应为0和755；Hikari等待峰值43和42。样本不排除采样间隔内的短暂队列波动，但已说明主要积压位于发布端，不能只增大消费者数量。数据见对应monitoring.json。

明确收益是积压和已观测投递等待下降。吞吐小幅差异不作为稳定容量增益的证明。最终将WAITLIST_OUTBOX_BATCH_SIZE默认设为100，范围仍为1至100；发布确认、mandatory退回判断、持久消息、认领租约、递增尝试令牌及SENT条件更新均保留，每条仍是短事务，未改为持有业务锁等待MQ。

同时在一次发布故障后结束当轮，保留既有退避及租约恢复，避免100条健康批量在代理故障时变成连续100次故障认领。中断标记保留。这部分是资源边界修复，不宣称健康RPS提升；新增测试核对认领次数与发送结果，真实故障用例再验证恢复。

## 未采用的调整

100 VU查询时监测到Hikari等待，默认10连接样本峰值等待91。仅扩大到20的一轮对照，RPS从1105.00到1210.45，P95从223.96到198.88毫秒，P99从402.00到333.12毫秒，见 [池大小对照](results/pool20/query-100/environment.json)。这是单轮、短窗口结果，缺少稳定收益与交易负载收益证据，因此没有修改生产默认连接池。

没有加入Redis缓存/库存预扣、分布式锁、异步下单、微服务或新的业务索引。读列表中存在小表排序，但SQL平均耗时不足以支持索引改动；不能因看到filesort就直接加索引。没有为了提升重复扫码数字跳过签名、账号或数据库状态校验。

## 保留的瓶颈与并发协议

100 VU热点基线中，SKU主键FOR UPDATE查询1500次，平均约160.97毫秒，累计约241461毫秒；COMMIT平均约6.79毫秒。最终代码相同热点SKU锁平均约169.48毫秒，锁协议没有消失。来源为对应 [基线SQL摘要](results/baseline/hot-ample-100/database.json) 和 [优化SQL摘要](results/optimized/hot-ample-100/database.json)。增加并发不会使同一库存行线性扩展，连接等待与行锁等待应结合看，不能仅凭HTTP200宣称抢票能力。

固定用户→活动→场次→SKU→订单锁序不变，候补和票券只在后续锁序内更新。用户行锁使同一用户跨场次写操作也串行；这是当前占额/释放协议的明确代价，本轮没有另建配额模型。单接口SQL次数、受控用户锁实验、已有索引计划以及慢查询统计保存在 [SQL和锁诊断](results/sql-and-lock-diagnostics.json)。限购SUM、FIFO队首、Outbox认领及分页以实测计划分析，没有凭经验新增索引。

关闭背景任务后的单次真实HTTP计数，创建/取消/支付分别记录20/19/22次SELECT、INSERT或UPDATE，包含身份复查及驱动会话状态读取，不包含SET和COMMIT，也不是20条业务查询。创建中的额外驱动读取包括1次隔离级别、3次只读状态查询。受控持有同一用户行至少250毫秒后，该用户两个不同场次请求分别375/422毫秒，不同用户为47毫秒；这用于确认锁覆盖范围，不能当作自然交易延迟或性能增益。

早期各轮database.json中的计划使用固定ID1，只用于保留SQL结构参考，不代表该轮夹具的实际参数选择性。回归后另以当前真实活动、场次、用户、SKU和订单ID补采完整联表计划，见 [实际参数执行计划](results/execution-plans.json)。这些计划来自当时较小的最终状态；压力期瓶颈结论依据上面的真实SQL计时和锁等待，未用小表计划推断生产规模性能或新增索引。

Outbox仍采用至少一次投递加数据库幂等。候补FIFO仅承诺同SKU队列内部，不优先于所有新购票；队首数量不足不得跳过。消息和后台任务通过重试、租约、死信与数据库补偿恢复，不宣称端到端Exactly Once。订单、库存、支付、候补联动及出票仍在原MySQL事务内，核销不改变库存。

## 原始结果及局限

完整同场景前后统计由 `python scripts/performance/report.py` 生成 [comparison.json](results/comparison.json)，每轮还保留JVM/Hikari、MySQL锁等待/SQL、RabbitMQ队列及Outbox样本。数据库计数差值含预热和消息排空，不能与20秒HTTP窗口直接相除混用。连接持有时间和Rabbit监听处理计时的补充对照单独保存，监听计时可含多次候补分配事务，并非单条SQL耗时。

库存审计在一致性快照中读取，核对边界及订单汇总、金额/支付、限购、候补归属/FIFO、票数和核销字段。指标按固定路由聚合，报告无密码、Cookie、有效凭证明文及签名密钥，k6初始化数据已剔除。

局限包括同一台机器共享压测器/应用/数据库资源、回环HTTP、短文本数据和20秒稳定窗口，没有独立生产网络/TLS、长时间浸泡、容量上限或统计置信区间验证。候补高峰投递仍可能等待数十秒，热点SKU串行瓶颈仍存在。真实支付、退款和整体模块解耦不在本阶段范围。
