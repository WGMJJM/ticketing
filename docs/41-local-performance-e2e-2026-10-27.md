# 本机性能与浏览器回归

2026-10-27 使用提交 `203c741` 的业务代码，在本机独立 Compose 数据库、Redis、RabbitMQ 和单个 Spring Boot 后端测试。JMeter 5.6.3、后端与容器均在同一台 Windows 机器；处理器为 i5-13400F，Docker 可见 16 逻辑处理器及约 15.5 GiB 内存。没有向本机业务库写入测试数据。

| 场景 | 负载和口径 | 实测结果 |
| --- | --- | --- |
| 活动详情，目录缓存开启 | 25 并发；5 秒爬坡、10 秒预热、30 秒正式窗口；固定同一活动 | 成功 367,079 次，12,235.97 RPS，成功样本 P99 25 ms，错误率 0 |
| 活动详情，目录缓存关闭 | 相同并发与窗口；禁用活动 Caffeine/Redis 缓存 | 成功 73,083 次，2,436.10 RPS，成功样本 P99 26 ms，错误率 0 |
| 普通购票 | 5 并发；40 个独立账号预热，正式窗口约 30.004 秒；每笔新账号和幂等键 | MySQL 窗口内 368 个成功订单，12.265 TPS；365 个成功端到端样本 P95 326 ms、P99 619 ms；无失败样本 |

购票端到端耗时从提交申请到轮询观察到成功订单，包含 250 ms 轮询间隔；登录、CSRF 不包含在耗时中，但每笔新用户登录会影响整体吞吐。提交完成时间与数据库创建时间不同，因此窗口内端到端样本数与订单数可以不同。该购票档位只是 5 并发下的结果，不能作为最大 TPS。活动读取缓存开启时主要为热点缓存命中；缓存关闭时 MySQL 缓冲池仍开启。每档只测一轮，这些数据不能代表生产部署或服务极限。

购票批次排空后 772 个正式申请全部成功；加上 40 个预热订单，MySQL 已锁定库存为 812，Redis 可售为 1,728，总库存 2,540，恢复队列和待处理数均为 0，订单关联差异为 0。

Playwright 使用真实 Microsoft Edge 156 和隔离应用，10 个场景全部通过：注册邮箱验证码、登录与权限、普通购票恢复、支付出票与凭证保护、幂等和限购、工作人员核销、退款、FIFO 候补、管理功能、场次取消、订单超时及申请超时。邮件由仅监听本机的测试 SMTP 收件箱接收；业务 HTTP 响应来自真实服务。随后 24 项只读数据库一致性检查全部通过。验证中修正了旧审计将候补订单误限定为普通购票操作域的问题。

隔离容器、专用数据卷、临时账号文件和本轮原始测试输出已清理；未执行生产环境压测。
