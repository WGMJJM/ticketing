# 500线程、256发布窗口的30秒实测

2026-10-28，按用户最新确认执行：500个JMeter线程，每个线程等待完整建单后换下一个独立买家；隔离实例购票在途容量1000，发布确认窗口256。仍是单SKU四桶、4消费者、prefetch=1。正式阶段不设目标RPS。

## 实测结果

先准备8000个独立登录买家，另20个账号进行原有低速启动检查。500线程的首批请求在并发预热阶段分10秒放行，正式阶段不再爬升。实际连续预热31.160秒，最近三个5秒段的成功完成率为36.2、42.0、36.4单/秒，满足极差不超过均值20%的稳定条件后，保持原负载继续测30秒。切换时仍有499笔未完成，未排空、重启或二次爬升。

| 正式窗口指标 | 结果 |
|---|---:|
| 窗内唯一MySQL订单 | **1131笔** |
| 真实订单TPS | **37.70** |
| POST / HTTP 202 | 1130 / 1130 |
| POST RPS | 37.67 |
| 完整建单P50 / P95 / P99 | **13.112 / 13.471 / 13.558秒** |
| 观察器确认P99 | 13.643秒 |
| HTTP POST P99 | 151ms |
| 每5秒订单TPS | 38.6、39.6、36.2、38.6、35.4、37.8 |
| 503、失败终态、UNKNOWN、重复订单、死信 | 全部0 |

完整建单指POST发起至MySQL建单提交并完成Redis预扣确认，包含排队，不包含支付。延迟只统计正式窗口发起并最终成功的1130个请求。TPS按已提交订单的`created_at`落入固定窗口统计，字段早于COMMIT的边界局限不变；预热期发起而正式窗内建成的订单也计入TPS，所以订单数与同窗POST数可以不同。

并发预热与正式阶段合计2779笔，全部成功建单。正式截止后495笔完成建单并排空，不计入37.70 TPS。账号预算未耗尽，最大已发放未完成请求恰为500，截止后新增POST为0。`wholeRunValid/correctnessValid/performanceCohortValid`均为true。
