# 8 桶与 16 桶对照

2026-10-28 按同一参数各运行一轮，使用独立空票档和互不重复的 8000 人登录账号。每档持续预热并稳定后，连续测量 30 秒；两轮均未重启、排空或中断负载。

| 参数/指标 | 8 桶 | 16 桶 |
|---|---:|---:|
| JMeter 线程 / 在途 | 200 / 200 | 200 / 200 |
| 隔离 Redis 购票容量 | 1000 | 1000 |
| 消费者 / prefetch | 12 / 1 | 12 / 1 |
| Hikari 最大连接 | 16 | 16 |
| RabbitMQ 发布确认窗口 | 256 | 256 |
| 稳定预热 | 36.343 秒 | 31.065 秒 |
| 成功订单 TPS | 79.60 | 82.07（+3.10%） |
| 受理至 MySQL 建单 P95 / P99 | 2.600 / 2.661 秒 | 2.481 / 2.552 秒 |
| POST 至 Redis 结算 P95 / P99 | 2.724 / 2.788 秒 | 2.595 / 2.659 秒 |
| HTTP POST P99 | 189 ms | 163 ms |

两轮均为单次测量，TPS 增幅只有约 3.1%，还不足以证明 16 桶有稳定优势。结果受测试顺序和单轮波动影响，暂不据此宣称性能显著提升。

两轮申请均全部成功且有完整结算样本，错误码、超卖、库存分配、额度、孤儿订单和死信均为 0；Redis pending、恢复集合、RabbitMQ ready/unacked 在排空后均为 0。逐桶审计的 MySQL 与 Redis 可售量一致。资源峰值均低于保护线：CPU 峰值 66.46% / 62.81%，RAM 使用率峰值 51.84% / 54.00%，可用内存最低 15.32 / 14.63 GiB；未触发熔断，后端均正常关闭。

现有 V15 数据结构已允许 16 桶，无需数据库迁移。为运行实验，在 `StockBucketRouter`、`TicketInventory`、`StockSnapshotService`、`TicketService` 和隔离 JMeter 夹具审计中补充了 16 桶支持；没有切换业务 SKU，也没有修改业务默认容量、消费者或发布窗口。路由单测通过，后端打包成功；未运行完整回归。

测试使用当前 `ticketing-jmeter` 隔离数据库，每组新建 60000 库存的空票档。每轮各领取 8000 个独立账号；账号池从 40000 一次补至 48000 后游标已用尽。没有连接或修改业务库、业务容器或业务数据卷。
