# SKU 锁内事务精简及 100 线程对照

## 结论和有效性

2026-10-27 在同一台 i5-13400F、约 31.82 GiB 内存的 Windows 主机上，以 100 个线程、100 个在途上限和不同账号测试单个 SINGLE 票档。两组分别运行 60 秒，均使用 2 个消费者、预取 1、Hikari 上限 10、购票容量 200 和 32 个发布确认槽位。Redis AOF `always`、MySQL 持久化、RabbitMQ 持久消息、安全限流、会话和 CSRF 保持启用；没有固定稳态 RPS。

**两组都发生 Redis 相关 503，且 A 组有一笔未采到结算完成时间，因此都不满足本任务的有效对照标准。下表只保留原始诊断结果，不计算 TPS 或 P99 改善百分比，也不把结果当作已验证稳定峰值。** 4、8 消费者及并发容量阶梯未执行。

| B 优化后 | 19:26:46.645–19:27:46.645 | 2155 / 2161 | 2064 / 34.400 | 310 ms | 3614 ms，2155 个样本 | 6 次 | 无效 |

TPS 按数据库 `ticket_order.created_at` 的窗口内唯一订单数除以 60 秒；窗口后分别完成 92 和 94 笔。受理 RPS 分别为 33.833 和 35.917，但不代表最终建单成功。A 组有 2 笔、B 组有 3 笔 HTTP 非 202 的申请最终建单；它们不能当作接口受理成功。完整建单耗时取 POST 至数据库事务提交并 Redis 结算的诊断记录，并非前台状态接口轮询耗时。

两轮实际线程数和在途配置均为 100，观测到的最大授权在途数均为 100。账号预先登录，各请求使用独立用户和幂等键；两个窗口分别预留 4300 个账号，未耗尽。初始两秒按实际发单时间错开，随后不设固定速率。两组还以约 4 次/秒的独立 PING 采样本机到 Redis 的延迟，该探针的额外开销没有独立 A/B 测量。

## 锁内顺序与修改

原始普通购票链路为：Redis 预扣和 RabbitMQ 发布确认；消费者在事务内协调并锁定申请，依次锁用户、活动、场次、用户场次额度和 SKU；SKU 锁后检查订单幂等和销售状态、增加额度、条件预占库存、创建订单和明细、复查申请截止并更新终态；事务提交后结算 Redis，随后消息 ACK。

本轮只修改锁内两处数据库往返：

1. `OrderReservation.insert` 原先先查询数据库当前时间，再插入订单。`OrderMapper.insertPurchase` 现在在同一条 INSERT 中以 `UTC_TIMESTAMP(6)` 写入创建、更新时间，并计算支付截止时间，仍使用数据库时间和数据库生成主键。
2. `PurchaseOrderWorker` 原先在成功终态写入前单独查询数据库时间。`PurchaseRequestMapper.finishSuccess` 将截止时间条件合入成功终态 UPDATE；更新未生效时仍查询数据库时间，区分已过期和异常，再沿用原事务回滚与失败仲裁。

这是合并 SQL 和调整时间判断时点，并非调整交易锁序。订单创建时间从单独查询数据库时间的时点移至 INSERT 语句时点；申请截止判断从成功更新前的查询时点移至 UPDATE 语句时点。因此，刚好在两者之间到期的申请可能由原先的成功变为过期，这是边界判定更严格的实际行为变化。到期竞争和回滚已有针对性回归，但未覆盖所有可能的跨模块高并发交错。

正常成功路径上，每笔建单的数据库时间查询由 4 次减少为 2 次：采样中 A 组 `OrderMapper.databaseNow` 和 `PurchaseRequestMapper.now` 均为 4064 次，对应 2032 个事务；B 组分别为 2158 次，对应 2158 个事务。订单幂等查询、最终申请回读、库存条件 UPDATE、额度、订单、明细和申请终态的同事务原子性均保留；没有调整锁顺序、删除显式 SKU 锁或修改 Flyway 迁移。

以下均为正式发单前到排空后的诊断计数差，**不是固定 60 秒窗口的精确样本**；锁后区间从客户端拿到 `FOR UPDATE` 查询结果到事务 `afterCompletion`，包括提交和回调，并非 MySQL 服务端精确持锁时间。

| 诊断指标 | A | B |
| --- | ---: | ---: |
| SKU 取锁查询平均耗时 | 4.588 ms | 4.526 ms |
| SKU 锁后客户端近似区间平均 | 22.864 ms | 21.058 ms |

采样均观察到 `ticket_sku` 主键 1 的锁等待，且事务提交占锁后区间较大部分。由于两轮无效且只测了一个消费者配置，不能据此给出可信的性能增幅或证明库存分桶必要。SKU 取锁 P95/P99 的固定窗口值未采集；滚动分位数不能冒充固定窗口结果。

## Redis 超时与资源

每个用户的购票安全频率上限是 10 秒 30 次。本次每个账号仅提交一次，`RATE_LIMIT_UNAVAILABLE` 表示 Redis 安全检查访问超时，不是用户达到次数上限，也不是所有用户共用一个 30 次额度。A 组出现 2 次该错误及 2 次 `PURCHASE_ADMISSION_UNAVAILABLE`；B 组各出现 3 次。两组均未记录 `slot_full`。

A 组四次 503 集中在窗口第 5 秒附近；同一时段独立 PING 出现一次 547 ms 的端到端延迟，超过 Redis 客户端配置的 500 ms 超时。B 组独立 PING 最大 422 ms，采样不能排除更短的尖峰。Redis 慢日志未记录超过阈值的命令，不能据此排除网络、连接排队、持久化写入或虚拟化 I/O；根因尚未确定。没有为测试调整 Redis 超时、关闭 AOF 或跳过安全检查。

窗口内 A/B 主机 CPU 最大采样分别为 44.17% / 39.83%，最小可用内存为 15.96 / 15.88 GiB；Docker 内存预算约 15.53 GiB。Hikari pending 峰值均为 0，采样最大间隔约 2.42 / 2.41 秒，未触发主机资源熔断。RabbitMQ ready 峰值分别为 94 / 96，低频管理数据不足以单独证明稳态；两组完成后 ready、unacked、Redis pending 和 recovery 均为 0。

## 正确性与验证范围

发布确认槽位的项目默认值由 16 改为 32，可显式配置 1–64。32 槽位下执行真实 MySQL、Redis 和 RabbitMQ 的 24 项针对性集成检查：包括 16 个不同用户竞争 8 张票、重复请求和重复消息、临界库存、过期竞争、故障回滚、支付、取消、退款及候补 FIFO，测试均通过。随后将临界库存场景扩大到 100 个不同账号、100 个并发请求争抢 32 张票：32 个请求受理并最终生成 32 笔订单，68 个请求返回库存不足，MySQL 库存和用户场次额度与订单一致，Redis 可售余额为 0。该场景单独重跑通过；它不能证明所有生命周期高并发场景均无风险，也没有测量 32 个确认槽位是否曾同时占满。

普通后端 `mvn -f backend/pom.xml verify` 的 108 项和 JMeter 脚本 14 项检查通过。功能测试使用独立 schema 和随机 guard，不使用业务库；功能测试沿用项目既有测试配置关闭用户频率限制，正式 JMeter 压测仍启用安全限流。该场景的临时 schema、验收账号、空队列和仅属于本次验收命名空间的 66 个 Redis 键已定向清理。

最终两轮审计中，订单关联、额度、重复订单、孤儿订单、库存与 Redis 余额差异均为 0；A/B 结束时库存分别为 `total=10000, locked=2052, sold=0, available=7948` 和 `total=10000, locked=4230, sold=0, available=5770`，没有死信，窗口采样没有观察到新增死锁。压力批次本身均为待支付订单，支付、退款等由上述独立功能用例验证；没有完成全部生命周期的高并发压力回归。
