# 四桶购票 30 秒单组验收

2026-10-28 在用户本机实际执行。用户执行中明确改为只测一组30秒，因此本轮只运行 **100线程、100在途、4消费者、prefetch=1、单SKU四桶**，不追加128/150档，不跑SINGLE或8消费者对照。没有证明机器极限，也不能据此计算分桶优化百分比。

## 实测结果

| 指标 | 结果 |
|---|---:|
| 固定窗口内唯一MySQL订单 | 1059笔 |
| 真实订单TPS | **35.30** |
| POST次数 / HTTP 202 | 1152 / 1152 |
| HTTP受理RPS | 38.40 |
| 窗口结束后排空建单 | 93笔，不计入35.30 TPS |
| 完整建单P50 / P95 / P99 | **2504 / 3463 / 3858 ms** |
| 观察器确认P99 | 3955 ms |
| HTTP POST P99 | 536 ms |
| 503、失败终态、UNKNOWN、重复订单、死信 | 全部0 |

“完整建单”从POST发起计时，到MySQL建单事务提交并完成Redis预扣结果确认。它包含排队、事务提交和Redis收尾，**不包含支付，订单仍为待支付**。保留工具兼容字段`postToSettledMs`，这里的settled不代表资金结算或支付完成。观察器确认耗时含约50ms诊断轮询传播，不是浏览器状态查询接口耗时。

主TPS依原口径按已提交订单的`created_at`落入固定`[startMs,endMs)`统计；该字段写入早于COMMIT，边界存在局限。以提交且Redis确认完成的诊断时间为第二口径时，窗内1056笔、35.20 TPS。MySQL与Windows采用最小往返样本校准，偏移-0.227ms、往返1.025ms。每5秒建单TPS依次为26.6、29.4、38.6、37.8、39.4、40.0，包含初始爬升，单个短窗口不能认定长期稳定平台。

`wholeRunValid/correctnessValid/performanceCohortValid`均为true。8000个正式账号预算未耗尽；每笔使用独立账号、会话、CSRF和幂等键，账号提前登录，不在计时窗内注册或登录。最大已发放未完成额度100，截止后新增POST为0，未触发熔断。

## 环境和安全

i5-13400F，10核16逻辑处理器，31.82GiB物理内存；Windows本机运行JMeter、Java21/G1、Docker。后端堆512MiB，JMeter堆256MiB；Hikari10，发布确认窗口32，购票容量200。实际运行证明确认Redis命令超时1s、连接超时500ms，4消费者/prefetch=1；Redis AOF开启且appendfsync=always，MySQL8.4.11的flushAtCommit=1/syncBinlog=1，Rabbit持久队列和消息发布确认保持开启。

正式窗CPU均值40.54%、最高53.10%，剩余内存最低16.32GiB；后端工作集最高456.69MiB，JMeter293.18MiB；连接池active最高4、pending为0。资源采样最大间隔2.584秒，主机磁盘PDH与容器BlockIO均保存。Redis实时pending最高98、5秒后斜率-0.79/秒；Rabbit管理采样ready最高93，其刷新延迟不作为实时持续积压证据。所有请求完成后排空，隔离JVM正常关闭，未强杀进程或中间件。

独立批次预建60000买家和60000库存；本次实际仅消耗8000个正式账号的预登录预算、1152次正式提交。隔离订单支付期限配置为120分钟，超时扫描继续运行，避免准备过程使旧订单到期混入测试；业务环境未修改。

初始化前逐条核实旧隔离功能测试残留消息的Redis终态和SKU，部分消息自然TTL过期，最终只清理261条已完成队列副本。旧三卷和原结果完整保留，新的guard隔离卷使用相同专用端口。功能验收配置已重新绑定新隔离卷并核验guard连接，未再执行额外负载。没有连接或写入3307/ticketing，未修改V1–V15迁移。
