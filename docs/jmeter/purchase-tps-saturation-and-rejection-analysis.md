# 单票档购票闭环饱和测试与入口失败归因

日期：2026-10-27。补充此前固定到达率诊断未完成的容量探索，使用当前普通购票链路，不做库存分桶或建单算法优化。

## 测量方法

此前 30 RPS→30 TPS、40 RPS→约40 TPS 只能证明跟得上输入，没有测出吞吐上限。本次依用户最新要求，以100个并发用户直接测完整建单链路，不设置RPS/TPS。每个JMeter线程提交后必须等自己的订单成功，才进入下一用户；最初一批在2秒内启动，随后由实际完成速度决定发单。正式窗口60秒，对照2/4/8个消费者时保持100个发压线程。固定窗口内MySQL独立订单创建数除以60才是TPS，窗口外排空另列。

HTTP 202不代表完成。MySQL事务提交且Redis结算返回成功后，默认关闭的诊断仪表记录无凭据终态及时间，仅保留最近512条。观察器约每50ms读取loopback内存记录，不访问数据库；测试线程看到自己requestId的成功终态才继续。JTL保存完整链路时间、观察时间及发放额度，事后按数据库核对每笔申请/订单。该模式属于相同并发用户的闭环对照，输入会随完成速度变化，不能冒充相同offered RPS的开放到达实验。

`postToSettledMs` 是发起POST至SQL已提交且Redis已结算的完整链路时间；`postToClientObservedMs` 是测试线程通过诊断观察器确认终态的时间，包含观测传播。前台查询接口未参与压力，不将这一时间冒充前台HTTP状态轮询性能。

实际主机为 Ryzen 5 5600H、6核12线程、15.856 GiB 内存；Docker 约7.683 GiB。后端 Java21 / G1 / 512 MiB堆，JMeter 256 MiB堆，MySQL8.4.13、Redis7.4.11、RabbitMQ4.1.8。只有隔离 `ticketing-jmeter` 项目、13307/ticketingjmeter、16379、15673/15674、18080/18081。原业务环境和数据卷未操作。

保持 Redis AOF always、MySQL flush_commit=1/sync_binlog=1、持久消息与发布确认、prefetch=1、Hikari=10、购票容量200、确认在途窗口16及原交易锁序。所有正式账号预先登录，正式窗口只有购票 POST，不发登录或状态轮询；每个账号只对应一个新申请。

## 入口错误到底表示什么

| HTTP / 错误码 | 实际触发条件 | 是否已经记录申请 | 正确解释 |
|---|---|---|---|
| 503 `PURCHASE_QUEUE_FULL` | Lua 检查全局未完成预扣数达到配置容量200 | 此次新申请没有预扣成功 | 应用在途容量已满，并非 RabbitMQ 队列存储满 |
| 503 `PURCHASE_ADMISSION_UNAVAILABLE` | SKU ready不为1、总计数/凭据缺失、Redis访问异常等 | 依具体失败位置而定 | 入口保护暂停，不能凭错误码认定消费者性能不足 |
| 503 `PURCHASE_PUBLISH_UNCONFIRMED` | Redis预扣成功后，发布槽位不足、确认超时、NACK、退回或发布异常 | 是 | 发布确认不确定，可能随后建单，必须沿用原幂等键查询/重试 |

`PurchaseRabbitConfig` 没有给普通购票队列设置 `x-max-length`。200 是 Redis Lua 的应用容量；16 是 `PurchasePublisher` 的共享发布确认并发槽位，二者都不是 TPS。

之前 20 次 `QUEUE_FULL` 的触发条件由 Lua 的 -2 分支明确限定。之前 36 次 `ADMISSION_UNAVAILABLE` 与旧订单到期、库存同步暂停入口有代码和时间关联，但当轮没有直接采到 ready=0，原因仍标为推测，不能写成已经确证。库存维护有合法的 pause→待预扣归零→发布绝对余额路径，不能为跑分停用。

本次第一轮24个HTTP发送线程、64个在途申请，发生128次 `PUBLISH_UNCONFIRMED`，这128笔随后全部建单；该轮保留并标为INVALID，不用于容量结论。随后增加默认关闭的发布诊断计数，以64个独立请求复现：13次503，与13次 `slot_full` 一一对应，`confirm_timeout`/NACK/退回均为0；64笔最终全部建单，确认ACK总数64，包含恢复发布。近期拒绝保护实际触发，停发后新增POST为0，排空和账目审计通过。这是失败原因复现，不是30秒吞吐测试。

正式组改为100个完整建单线程，保留发布窗口16、容量200及原消费者预取1；没有调大容量、取消保护、把失败请求换新键重试或剔除失败样本。24线程突发异常完整保留。

工具调试还保留了两轮作废结果：一轮Rabbit管理统计延迟跳变触发错误的持续增长判定（777笔均建单）；另一轮Windows文件共享冲突使完成观测失败（80笔均建单）。前者改以实时Redis在途数判定增长并补回归测试，后者加入有界100ms文件替换重试，持续失败仍停发。100线程首轮发生1次发布槽位满和7次观测JSON读取异常，最终均建单；其48.783 TPS仅列诊断，不作为无异常基准。后续在同一文件句柄读完整JSON、对瞬时读取异常有界重试，并区分网络错误与观测错误。默认2消费者完整复测未发生读取重试或拒绝，对账通过。

## 结果与证据

三组均为100个完整建单线程、60秒窗口，无目标RPS。有效轮次合计9632笔请求均完整建单并观察终态，入口拒绝、终态失败、缺失样本、重复及孤儿均为0。窗口外订单只用于排空核对，不计入TPS。

|---|---:|---:|---:|---|---|---:|
| 2 | 3023/3023 | 2927 / **48.783** | 96 | 2244/2599 ms | 2317/2658 ms | 48 ms |
| 4 | 3038/3038 | 2943 / **49.050** | 95 | 2445/2486 ms | 2516/2546 ms | 70 ms |

2→4吞吐仅增加0.55%，基本没有改善；2→8本轮增加18.72%，并非消费者数的四倍。它是本机本次单热点SKU的实测变化，不是生产环境保底收益。三个窗口内部也有波动：4组每5秒为40.6–65.4 TPS，8组为40.0–66.8 TPS；不将短片段峰值当作持续能力。最高完整60秒平均为57.917 TPS，不宣称机器所有场景的绝对上限或长期恒定吞吐。

### 限制吞吐的环节

下表为正式发单前至排空后计数/总耗时差得到的消费者阶段均值。阶段存在包含关系，不能相加当总时间。SKU持有区间是锁定查询返回至事务afterCompletion的客户端近似，包含提交，非服务器精确持锁时间。

| 阶段均值 ms | 2消费者 | 4消费者 | 8消费者 |
|---|---:|---:|---:|
| 消费者整笔处理 | 39.573 | 79.931 | 136.918 |
| 数据库事务总时长 | 30.460 | 64.169 | 125.289 |
| SKU锁定查询，含等待及往返 | 1.473 | 29.618 | **93.648** |
| SKU取得锁后至事务完成 | 15.404 | 20.274 | **17.237** |
| 预占、订单与明细写入 | 7.644 | 8.181 | 8.148 |
| 事务提交调用，含连接收尾 | 6.049 | 10.357 | 7.307 |
| Redis凭据读取require | 2.235 | 4.102 | 2.951 |
| 提交后Redis结算settle | 5.734 | 10.457 | 7.489 |

**主要限制是热点SKU的锁内事务。** 4/8组Performance Schema分别采到39/393条 `ticket_sku|PRIMARY|1` 等待关系；全局行锁等待时间增量分别81.241/301.822秒。全局累计量不全归给单SKU，主键等待关系才是直接定位证据。8组取锁查询已占事务均值约74.7%，更多消费者主要排队等待同一行。17.2ms客户端持有区间对应约58次/秒的数量级，与57.9 TPS接近；这是结合等待关系的支持证据，不是精确容量公式。

**锁后多次SQL往返及提交延长了串行区间。** `OrderReservation.reservePurchase/insert` 在锁后继续查订单幂等、读数据库时间两次、增加额度/库存、插入订单和明细；`PurchaseOrderWorker` 随后再次读截止时间、更新申请终态并回读，直到事务提交才释放锁。2组这些Mapper调用大多约0.9–1.2ms，单条不慢，但多次往返累积在锁内。服务器COMMIT digest均值分别3.508/7.527/4.573ms，说明提交路径确有成本；不能把客户端commit全部解释为fsync，也尚未分解存储等待、调度和网络的份额。

**默认两个消费槽位及提交后的Redis工作也限制处理能力。** 默认组每笔39.57ms，两个槽位的简单估算约50.5单/秒，与48.8 TPS接近。Redis结算在SQL解锁之后仍占用消费者，平均5.7–10.5ms；增加消费者后SKU锁竞争显著上升，所以只扩消费者不能按比例提高吞吐。Redis网络往返与AOF等待未进一步拆开，不将全部耗时归为Lua执行。

## 校验与保留现场

新增发布及完成观测仅在 `ticketing.diagnostics.enabled=true` 生效，分类计数不改变槽位获取、确认等待、恢复或订单处理语义。`mvn -f backend/pom.xml verify` 实际108项通过，0失败/错误/跳过；新增测试核对槽位耗尽、ACK归还、NACK、超时不提前归还、默认无诊断计数及终态记录有界。Python统计/保护/Windows瞬时文件共享测试11项通过。真实100线程三组均完成，未执行前端构建或mysql-it全业务套件，不据此宣称全平台功能回归。

两批最终只读审计分别在17:37:51及17:50:46完成：6117/6649条申请、订单与明细一一对应，含预热与前期探测；申请均SUCCEEDED，订单均PENDING待支付。库存locked分别6117/6649，与订单汇总及Redis一致；金额、额度、重复、孤儿审计均0异常。普通MQ、Redis在途/恢复集合均排空，无重投、死信或其他活动事务；支付、候补、电子票、库存桶及分配记录均0，库存Outbox事件0。购票完成不等于支付完成，也不等于未来超时任务已执行。

旧隔离批次在guard、卷标签、应用端口、在途购票和数据库事务核验后停止并移除其三个容器；旧数据卷、凭据及结果全部保留，新批次使用新命名卷。测试JVM均正常关闭，未强杀在途事务。没有删库、删卷或清理业务资源。所有原始JTL、会话、CSV及运行配置均保留本地并被Git忽略；共享证据即以上去敏汇总及可复现脚本，不提交凭据。
