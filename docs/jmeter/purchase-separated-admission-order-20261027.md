# 分离购票受理与异步建单的本机测试

2026-10-28 清理说明：本报告涉及的旧压测卷和本地原始产物已删除，以下仅保留历史结论；后续执行使用当前 JMeter 入口。

## 环境、数据和安全边界

2026-10-27 在 Windows、i5-13400F、16 逻辑处理器和约 31.8 GiB 内存的同一台机器上运行 JMeter 5.6.3、Java 21.0.10、单 Spring Boot 实例、MySQL 8.4、Redis 7 和 RabbitMQ 4.1；Docker 可用内存约 15.53 GiB。**实际测试的业务代码为 `a66a69574ff26f9cdea0475b097da3fa18573e2c`**。测试结束后用户要求拉取最新代码，本地已快进至 `3fb128e`；本报告不能视为已测该新提交。

所有请求都发送到独立 `ticketing-jmeter` 项目和 `127.0.0.1:18080` 应用，独立 MySQL 为 `127.0.0.1:13307/ticketingjmeter`，Redis/RabbitMQ 及卷均为专用资源；测试前检查项目标签、端口、卷、随机数据库 guard 与健康状态。仅该实例设置 `ticketing.purchase.capacity=1000`；消费者 2、prefetch 1、队列期限 120 秒、发布确认在途 16、超时 3 秒，未修改生产默认值。真实 Session、CSRF、限流、库存、额度、幂等和 MQ 发布确认保留。

固定一个无有效候补的 SKU，单笔一张，总库存 5,400。预先真实登录并通过 `/auth/me` 校验 5,350 个独立账号及会话，8 个准备线程耗时 126.81 秒；后来为更低负载安全复核追加 1,020 个独立账号，预登录耗时 36.66 秒。各档账号不重叠；每档预留数分别为 350、700、1,400、2,900，即目标发单数加该档线程数，测前核对库存与可用会话。500 线程档单独有 2,900 个账号，理论上按单次购票和 30 秒最多约 96.67 笔/秒；本实现还为线程预留 500 个会话，因此按目标 80 RPS 配给 2,400 笔。资源预算不是能力上限。

发单只调用 `POST /api/v1/orders`，使用预登录 Session、CSRF 和唯一幂等键，发单线程不登录、不轮询。负载到达按时间槽控制，每档爬坡 60 秒，随后固定 30 秒窗口；正式结束停止新 POST，之后只读核对 Redis、RabbitMQ 和 MySQL，并有限等待排空。JMeter 测得 HTTP 202 且申请 ID 有效的受理 RPS 和 POST P99；数据库创建 TPS 按该批次 `ticket_order.created_at` 处于窗口内且关联 `SUCCEEDED` 申请计算。成功申请的服务端延迟为 Redis Lua 记录的 `accepted_at` 至 MySQL 订单行 `created_at`，按最近秩计算；它不包含客户端 POST 网络时间、也不是事务提交完成或客户端观察时间。

测前 MySQL 时钟相对本机偏差小于约 0.4 ms，Redis 预热后小于约 0.8 ms，往返约 0.5–1.1 ms；测后再次检查无明显偏差。资源监控会带来一定开销，单机数据不能作为线上峰值或长期容量。

前四档每个窗口使用独立批次，500 档每秒 POST 数依次为：`80,80,80,80,80,80,80,80,79,81,80,80,79,80,81,80,80,79,80,80,81,80,80,79,81,80,80,80,1,0`。500 线程在前 28 秒的请求响应采样中均处于活动状态，保护触发后线程退出；窗口中同时在途 POST 的峰值为 18，不等于 500 个并发 HTTP 请求。463 个拒绝来自容量保护，不计入成功受理；1,778 个有效受理全部最终成功，队列在窗口后约 27.4 秒排空。40 RPS 档队列约 9.9 秒后排空，不应把其受理率当作稳定建单能力。

用户随后补充了更严格的本机保护要求。上表各档在补充前运行，资源采样大约 3–6 秒；其中 20 RPS 是本轮**较早的无错误、无持续积压基线**，但采样频率不满足随后提出的约 2 秒要求，不能称为按新要求完整验证的最终极限。

## 新保护及后续低负载复核

更新后的监控以约 2 秒采样主机 CPU、可用物理内存及后端/JMeter 进程，异步采集 Docker、RabbitMQ 和 MySQL。CPU 高于 85% 持续 15 秒或高于 95% 持续 5 秒、物理内存占用超过 85% 或剩余不足 4 GiB、Docker 用量达到 85%、严重 Full GC/OOM、监控不可用、队列持续积压/满或持续大量错误时，创建 `stop.flag`，JMeter 在发单前及等待时间槽时读取标记并停止新请求，已受理请求继续排空。对持续 85% CPU 或队列积压，本实现停止当前发单，比只停止升档更保守。

用 10 线程、小流量模拟保护停止标记：标记后新增 POST **0**，已受理请求正常排空；采样记录间隔约 2.00–2.02 秒。CPU、内存和队列阈值另以合成输入验证；没有为验证而故意耗尽本机资源。

已有 40 RPS 持续积压、80 RPS 队列满，因此未再挑战更高负载；仅向下尝试 30 RPS。该档约 6 秒内发出 172 次，84 次受理、88 次返回 `503 PURCHASE_ADMISSION_UNAVAILABLE`，保护停止发单；84 个已受理申请最终均成功。停止前约 6 秒内，数据库记录 56 笔旧订单到期。库存维护实现会暂停票档入口并等待预扣结算后同步；此现象与到期处理时间重合，但同一 503 也可能来自 Redis 受控故障，缺少逐次维护状态证据，不能认定为唯一原因。

库存恢复、队列为空及账实核验通过后，仅以更低的 20 RPS 按新保护复核：597 次 POST 中 547 次受理、50 次 `PURCHASE_ADMISSION_UNAVAILABLE`，保护在窗口末尾停止；547 个已受理申请全部建单。该档窗口内建单 547 笔、成功样本服务端 P99 300.103 ms，但因错误率和保护触发，**不属于稳定性能**。窗口内有 100 笔旧订单到期，仍不能把拒绝简单归因于某一原因。按新保护要求，本轮尚未取得完整 30 秒、零持续积压且错误可接受的稳定档位，因此**不能给出符合新要求的最高已验证稳定 RPS/TPS**。

## 瓶颈证据与正确性

前四档中 20 RPS 的受理、消费和建单基本匹配；40 RPS 时 RabbitMQ 采样发布约 40.3 条/秒、ACK 约 34.2 条/秒，ready 达 154；80 RPS 档 ready 达 998、两个消费者持续有未确认消息，并触发队列容量拒绝。40 档 MySQL 全局行锁等待计数在窗口采样间增加 298 次、累计等待时间约 2,692 ms；80 档增加 285 次、约 3,150 ms。Performance Schema 的 SKU `SELECT ... FOR UPDATE` 在各档采样期的平均执行时间约为 0.207、0.463、3.019、2.688 ms；这是累计 SQL 汇总，不能单独证明等待均由 SKU 引起。全隔离库死锁错误计数为 0。

本轮前四档主机 CPU 采样最大值分别约 20.7%、25.4%、33.7%、31.9%；JMeter 进程约 0.06、0.09、0.18、0.32 个逻辑核心，采样未见连接池等待栈。新保护复核中主机 CPU 最高采样约 64.1%、物理内存剩余约 16 GiB 以上，没有资源阈值触发。CPU 和内存不是这几档中已观察到的限制；低频采样不能排除短时峰值。未隔离测量 publisher confirm，因此不能单独判定它的耗时。

上轮闭环 500 用户结果为 8.433 TPS、客户端观察 P99 43.257 秒，且每 250 ms 轮询、窗口内有 39,742 次状态查询和大量连接池等待。本轮去掉发单线程轮询后，低档受理及建单明显不同，支持“闭环用户等待和轮询竞争影响了旧模型”的判断；两轮负载、时间口径和背景资源不同，不能将差异全部归因于轮询，也不能据此宣称业务性能提升倍数。当前证据显示更高输入率下消费者/数据库链路跟不上，SKU 锁和消费者槽位可能相关，但还不能确定唯一瓶颈。

最终只读核验时，4,537 个购票申请均有对应成功建单事实，订单关联异常、重复订单及重复关联均为 0；由于核验时已过支付期限，4,537 个订单均已正常 `EXPIRED`，MySQL 库存总量 5,400、锁定 0、已售 0，Redis 可售 5,400，预扣和恢复索引均为 0；购票队列及死信队列为空。未人为修改业务事实来使对账通过。
