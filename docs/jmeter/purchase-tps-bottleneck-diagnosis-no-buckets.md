# 购票 TPS 瓶颈诊断 不启用库存分桶

本文件是初轮固定到达率诊断，未测出容量上限。后续已补充100线程完整建单的2/4/8消费者对照，实测及瓶颈证据见[完整链路并发报告](purchase-tps-saturation-and-rejection-analysis.md)。

日期：2026-10-27。本轮只增加隔离观测、发压与统计工具，没有修改建单算法、锁序、库存策略、事务隔离、鉴权或生产默认参数。

## 1. 判断与证据边界

**已经确认的是消费积压和另一类库存维护门禁干扰；尚未证明 SKU 行锁是唯一主瓶颈，也未证明应扩大连接池或实施分桶。**

- 2 消费者、60 offered RPS 出现持续积压、容量拒绝并触发停止。入口 HTTP P99 为 38 ms，服务端受理至建单 P99 为 3801 ms，瓶颈落在受理后的处理链路，不是 HTTP 接口本身耗时数秒。消费者单笔均值 41.10 ms，事务 32.37 ms、提交后 Redis 结算 5.26 ms；仅两个消费槽位是值得优先对照的限制，置信度中等。没有完成相同高负载的有效扩容对照，不能声称增加消费者已提高某个百分比。
- Hikari 采样 pending 均为 0，池未用满，低频线程快照未捕获 `ConcurrentBag.borrow`；借连接均值很小。本轮不扩大池到 16/20。采样不能排除短促等待，但不支持“连接池是主要瓶颈”。
- 已捕获 `ticket_sku PRIMARY=1` 的排他行锁等待，且 SKU 锁后至事务完成约 15 ms，说明热点锁存在且有压缩空间。原 40 RPS 对照中 2 消费者取锁均值仍很小，不能把“存在锁”和“锁决定了最高 TPS”画等号。
- 原票档的 8 消费者组出现 36 次 `PURCHASE_ADMISSION_UNAVAILABLE`，并非 `PURCHASE_QUEUE_FULL`。同阶段旧订单到期、库存序列推进，代码存在先暂停受理再同步绝对库存的路径。此轮标为 INVALID；门禁干扰的判断有代码和时间关联，未直接采到该轮 Redis `ready=0` 的瞬间，因果置信度中等。为隔离票档门禁，保留旧数据，新增普通 SINGLE 票档后重新进行同负载三组对照。

没有客户端首次观察终态的采样，**客户端端到端 P99 未采集**。以下服务端 P99 以 `purchase_request.accepted_at → ticket_order.created_at` 计算，后者早于提交结束，不冒充客户端观察或事务提交完成时延。

## 3. 发压模型与固定负载对照

每组预登录完成后，独立 20 账号预热并排空，正式窗口固定 30 秒。JMeter 按绝对到达时间发 **POST only**，没有登录、CSRF 请求或状态轮询。每笔独立 Session、账号、幂等键；统计以 `postStartMs/postElapsedMs` 为准，JMeter 自带 elapsed 包含节拍等待，不能用来报告 HTTP 延迟。

正式 TPS 严格按该批次唯一 CREATE_ORDER 订单的 MySQL `created_at` 落入预先确定的 `[start,end)` 计算。固定窗口结束后建单另列，全部 202 事后按幂等键和 requestId 对账。分位数采用最近秩，不剔除失败请求；服务器成功样本明确单列。

## 5. SKU 锁与事务拆解

原 `ticketing.trade.lock.duration{resource=stock}` 包含 Mapper、网络及可能的锁等待，**不是持锁时间**。新增 `stock.held.client` 从锁定查询返回到事务 `afterCompletion`，覆盖提交，是客户端近似持有区间；服务器实际取得/释放锁与客户端回调之间仍有往返和调度偏差。

当前 MyBatis-Plus 3.5.17 的 `selectOne` 实际使用 `selectWithCursor/queryCursor`。仪表覆盖常规 query、六参数 query 和 cursor，不遍历或提前关闭结果。仅对真实存在 SKU、成功事务数与持锁计数一致的组解释持有时间；空游标不构成已有行锁持有证据。

这些阶段互相包含，不得相加当总时间。取连接事务入口还包括连接状态/隔离级别设置，不等于 Hikari 排队。阶段总量覆盖正式发单到排空，严格窗口指标另由 DB/JTL 提供。

`worker.process` 不包含监听器进入前的消息传输/反序列化及返回后的 AUTO ACK 往返；这些阶段未单独计时，无法进一步归因。提交后 Redis settle 已单列。阶段与连接池分位数都是滚动估计；只有 HTTP 与申请到创建的分位数来自本批次完整逐笔样本。

2/40 的持有区间约占事务均值 **50.1%**，4/40 约 **47.5%**。锁后主要还执行：订单幂等查询、数据库时间查询、额度条件增加、库存条件增加、再次取数据库创建时间、订单 INSERT、明细 INSERT、申请截止复查、申请终态 UPDATE 与回读、生命周期协作及提交。`transaction.commit` 另包含解锁后的连接状态重置等收尾，不能全部算为持锁。锁内有多次 SQL 往返，不能把所有持锁时间归为库存 UPDATE 一条语句。

原 4/40 的 Performance Schema 采到 3 条等待关系，均指向 `ticket_sku` 的 `PRIMARY`、`LOCK_DATA=1`、`X,REC_NOT_GAP`。该轮全局行锁等待增量 65 次 / 1483 ms，但全局值包含后台任务，不能全归给普通建单。2/40 仅增量 26 次 / 48 ms；两轮均未发生死锁。

4/40 的 digest 正式前至排空差：COMMIT 1246 次 / 3548.60 ms，SKU FOR UPDATE 1202 次 / 2176.79 ms；其他代表性语句如库存 UPDATE 1200 次 / 305.50 ms、订单 INSERT 1200 次 / 317.38 ms。digest 包含后台任务且计时在服务器侧；Mapper 客户端计时不是纯 MySQL 执行时间。上述证据支持检查提交及重复往返，仍不足以推导单 SKU 极限 TPS。

没有进行单 SKU / 四 SKU 扩展性实验。新增 SKU=2 用于隔离旧票档受理门禁，**不是**单/多 SKU 吞吐因果对照。

## 6. 所测吞吐与稳定性限制

完整 30 秒的最高所测建单吞吐是 **39.967 TPS**，两组各 1199 窗内订单、1 窗外订单。它只代表这两次短窗口；没有长期稳态测试，没有找到系统最大能力，也不能称“长期最高稳定 TPS”。

60 RPS 的 26.467 TPS 包含主动停发后的空闲时间，不能作为最大处理能力。8/40 的 35.933 TPS 同样无效。没有为了提高指标扩大容量、停用到期、绕过签名或降低持久化。

## 9. 下一阶段建议 仅方案

1. **先补足高负载对照。** 保持独立账号、POST only 和当前安全条件，在新隔离批次、尚未跨越支付到期窗口时对比 2/4 消费者。当前 2 槽位和 37–41 ms 整段处理值得优先检查；本轮低负载对照不能直接支持修改生产默认值。
2. **优先评估缩短持锁与连接占用。** 审查锁后幂等回读、数据库时间查询、申请终态回读与提交路径。任何合并/前移都必须保留数据库时间截止、唯一键、准确金额、固定锁序、同事务订单/额度/库存及生命周期；先证明语义再对照，不能直接删校验。
3. **单列超时扫描、释放与库存快照门禁可用性。** 在保持有界逐单事务及暂停→排空→绝对余额发布安全协议的前提下，测量扫描积压、ready=0 持续时长、刷新重试与事件合并机会。全未支付实验还须匹配到期处理预算；先区分维护拒绝与消费排队，不能用“扩大 MQ”解决 `ADMISSION_UNAVAILABLE`。
4. **池大小保持 10。** 只有后续出现持续 pending、消费者 borrow 栈和 acquire 等待，且 MySQL 有余量时，才做 10/16 同负载实验。
5. **目前没有必要直接实施库存分桶。** 先补高压因果对照、确认 SKU 等待和持有区间随负载增长的占比，再考虑正常多 SKU 诊断。只有消费者扩容无收益、确有单 SKU 串行瓶颈时才评估复杂库存方案；本轮没有实施或启用分桶。
