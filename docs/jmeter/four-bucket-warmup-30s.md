# 连续预热后测量30秒

2026-10-28，本机隔离环境实测。仅调整既有诊断脚本的阶段衔接与统计，不修改业务代码、持久化设置或并发参数。

## 方法与衔接证据

保留原有20笔低速启动检查；随后同一JMeter以100线程、100在途持续预热，保持四桶、4消费者、prefetch=1、发布确认窗口32。Redis命令1s、连接500ms，AOF always、MySQL事务持久化和Rabbit发布确认保持原配置。

满30秒后，最近三个5秒段的成功建单完成率为49.2、49.2、46.8单/秒，极差小于均值20%，进入正式30秒。以实际第一笔POST计，预热31.079秒；计划时间记录为31.153秒。切换时仍有97笔未完成请求，两个阶段没有排空、重启、暂停或重新爬升。证据保存在`warmup-audit.json`。

未稳定时每5秒复查，预热最多60秒；仍不稳定则停止，不冒充已经进入正式测量。账号预算覆盖预热和正式全过程，正式计时窗内不登录或建号。

## 正式结果

| 指标 | 实测 |
|---|---:|
| 正式窗口 | 30秒 |
| 窗内唯一MySQL订单 | 1493笔 |
| 真实订单TPS | **49.77** |
| 正式POST / HTTP 202 | 1492 / 1492 |
| 完整建单P50 / P95 / P99 | **1922 / 2104 / 2167 ms** |
| HTTP POST P99 | 134 ms |
| 正式每5秒TPS | 49.0、49.6、50.8、48.8、50.8、49.6 |
| 503、失败终态、UNKNOWN、重复订单、死信 | 全部0 |

“完整建单”包括MySQL事务提交及Redis预扣确认，不包含支付。P99只使用正式窗口发起的1492笔成功请求，包含它们在截止后完成的耗时。TPS按MySQL订单创建时间归窗，包含预热期发起、正式窗内创建的订单；所以窗内订单数与正式POST数可以不同。`created_at`早于COMMIT的原有边界局限保持公开，不将其当作精确提交时间。

并发预热与正式阶段共发3022笔，全部成功；93笔在正式截止后建单并完成排空，不计入49.77 TPS。账号预算未耗尽，实际在途未超过100，截止及保护停止后新增POST均为0。`wholeRunValid/correctnessValid/performanceCohortValid`均为true。本轮只证明此负载下的短窗口表现，不证明本机极限；测量方法与此前包含爬升的35.30 TPS不同，不计算代码优化提升百分比。
